# ACT secondary analysis tools

This 2026-10-26 investigation defines functional targets for the
[desktop GUI plan](gui-plan.md), extending the tree/action/log workflow.
It compares decompiled ACT 3.8.5.288 with current aftercast source; the report
windows below were not exercised with a populated reference encounter in this
pass. Code-confirmed behavior must not be described as runtime-verified parity.

The installed reference SHA-256 was checked again:
`934fc00d0a3c8325b0f7445358860b4c013c5dab3d8fff012512acf6502dd657`.
Local reference extracts are retained under
`target/design-reference-act/current/` and are not distributed source files.

The first avoidance outcome grouping slice and its remaining reference questions are documented in [avoidance-outcome-contract](avoidance-outcome-contract.md).

## Workflow and design targets

| Tool / origin                      | Reference behavior found in code                                                                                                                                                                                                                                                                                                                                                                                                               | Target for the next B-based design                                                                                                                                                                                                                                                                   |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Death report / combatant           | Finds `Dnum.Death` actions in incoming actions; offers individual death selection, damage/healing chart, per-second text and action tooltips. Initially selects the last death. Text can be copied in full or by selection; chart can be copied/saved                                                                                                                                                                                          | Show a death selector and the incoming damage/healing context around that death. Keep combatant/encounter identity visible and offer underlying action inspection. A death count alone cannot provide this workflow                                                                                  |
| Avoidance / combatant or encounter | Separates failed/no-damage outcomes using `Dnum` values and display text, excluding death markers when collecting damage actions. Combatant results group by registered damage categories and include occurrence proportions; encounter results select outcome labels containing an ally name or `YOU`. Both include estimated avoided damage and contributing attacker/skill/sample/count details on activation, with an optional copy action | Make combatant versus encounter scope explicit. Provide clear denominators where proportions exist and expandable supporting samples. Label avoided damage as an estimate. Report activation opens sample evidence, which is a different operation from activating an individual action's source log |
| Special attacks / combatant        | Groups outgoing damage actions by skill + special, skill with any special, and special type. Uses registered damage swing types and `GetAttackSpecials()` counts, including reference `ANY`/`ONCE` conventions                                                                                                                                                                                                                                 | Show grouped special-event counts and skill context. Preserve the distinction between total special occurrences and actions with a special; one generic critical-hit percentage is insufficient                                                                                                      |
| Timeline / encounter               | Plots selectable outgoing/incoming damage/healing series, individual or grouped participants, rolling averages or segments and sample duration. Has participant visibility and zoom controls. Right-click resolves a plot time and opens a separate log window                                                                                                                                                                                 | Use a time-series view with explicit metric, grouping and sample window. Keep the encounter context when opening logs. A plot time denotes a time range/location, whereas an individual action has a specific source identity                                                                        |
| Recast calculation / attack        | Sorts actions by time, allows inclusion/exclusion, plots a delay-frequency distribution, and supports short-delay filtering plus a game-specific recast adjustment. Timer handoff fills skill name, attacker category, modifier setting and calculated delay, then offers to add/edit                                                                                                                                                          | Show selected actions, interval distribution and the proposed timer duration. Allow review before committing a timer definition. Explain exclusions and insufficient samples; do not infer a cooldown from aggregate DPS                                                                             |
| Encounter VCR / encounter          | Has play/pause, rewind/fast-forward, time seek, category filters, history traces and optional active-encounter following. Nodes are arranged by generated ring/group layouts; edges summarize recent outgoing actions by target/category. Health is inferred from model maximum health and incoming damage/healing                                                                                                                             | Treat this as a temporal interaction diagram. Make current time, lookback and follow mode visible. Inferred health must be labelled; generated node positions must not be presented as game-world movement or coordinates                                                                            |

These are workflow requirements, not instructions to preserve ACT's form layout,
radio-button transport controls, clipboard confirmation wording or exact chart
styling. Initial context-menu entries may open dedicated views or nonmodal
windows, but changing the main selection must not silently change an existing
report's origin. Live following must be an explicit mode.

documentation pass. Empty lists, unavailable actions/logs, stale session IDs and

## Data prerequisites and delivery order

Current [combat queries](../crates/aftercast/src/combat.rs) and
[snapshots](../crates/aftercast/src/snapshots.rs) provide aggregates; they cannot
reconstruct the ordering, individual outcomes or attacker/target evidence above.
Managed [MasterSwing](../managed/ActCompat/MasterSwing.cs) and
[Dnum](../managed/ActCompat/Dnum.cs) hold richer action/outcome information.
No dedicated report implementation was found in the current managed/Rust
sources inspected for this pass.

| Order | Required capability                                                                      | Reason                                                                                                                                                                         |
| ----- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1     | Session-scoped action identity, ordered bounded action queries and action-to-log linkage | Shared prerequisite for drill-down and evidence inspection; resolve recording/restore gaps in the GUI plan first                                                               |
| 2     | Registered categories/swing types, allies and action outcome metadata                    | Damage/healing/avoidance semantics come from parser registrations, not fixed English labels or positive-number assumptions                                                     |
| 3     | Bounded report queries or bounded host-side aggregation with origin/revision context     | Avoid transferring every action on each render; keep callbacks and mutable model access on the host owner thread. Define report consistency if live data changes during paging |
| 4     | Death context, timeline and recast report surfaces                                       | Directly useful analysis tools; timer handoff depends on the separately planned definition editor/save contract                                                                |
| 5     | Avoidance/special reports and VCR                                                        | Require additional estimate/grouping/playback comparisons. Keep them explicit planned capabilities rather than suggesting the first aggregate GUI already has parity           |

For visual exploration, show one connected secondary-tool flow alongside the

### Action projection foundation

The bounded encounter action query now returns the original signed `Dnum.Number`, swing type, critical flag, nullable special/damage-type strings and nullable raw Dnum label/suffix, alongside the existing display text and source-log link. Raw negative values are preserved, including ACT outcome sentinels; callers must not infer damage, healing or miss classifications from localized display text. Swing-type registration and category membership determine those meanings and remain separate work requiring an owner/revision-bound contract. The same swing type may be registered for multiple categories.

New private history payloads preserve these raw fields and distinguish null from an empty label/suffix; legacy or ordinary ACT interchange records without private number attributes can use display-text fallback, so historical raw fidelity is not guaranteed there. The page is a live bounded query, not a frozen multi-page snapshot. TimeSorter links source logs only when unique and is not a durable action ID; duplicate sorter values retain ambiguous source links.

Action snapshots capture canonical outgoing rows and the plugin-registered damage/healing swing-type membership together. Both membership flags may be set or clear; they do not reinterpret Dnum outcome sentinels. A session owns one snapshot, and a later capture invalidates the previous revision. Captures exceeding 16,384 rows fail explicitly; pages remain fixed when the graph or registration changes. Source indices address the log pages captured under the same revision, including the recorded dropped-line count; do not apply them to live log pages. Captures with more than 65,536 retained log rows fail explicitly. This is a bounded projection, not a durable action identity or a byte-bounded copy of the encounter graph.

L8b prerequisite: outgoing canonical actions do not cover an incoming-only swing registration. The managed host can capture one combatant's incoming `All` list with the same snapshot and log ownership rules; The owned Bridge/Rust API exposes this incoming capture; the death report UI is not yet connected. Death recognition must use `Dnum` equality, not merely the numeric sentinel: a `-10` value with a custom non-Death label is not equal to `Dnum.Death`. The snapshot carries this equality result without discarding the raw value or label. The [death report contract](death-report-contract.md) now resolves bucket aggregation and ordering through original IL and executable synthetic data-class fixtures. The populated native report window remains unverified.
