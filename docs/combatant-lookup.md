# Lookup by combatant

ACT `FormByCombatantLookup.ShowLookup` copies the selected category’s `All` actions, groups outgoing by victim and incoming by attacker, then adds each action to both the peer’s `All` and named attack. An attack named `All` therefore appears twice in that aggregate. Selecting a skill shows its actions; source category and direction remain explicit. These observations are from the decompiled ACT code, not a native-form run.

Aftercast captures the selected category and matching source logs together under the combat lock using the existing action snapshot lifecycle. Rows and log identities are bounded by the existing 16,384-action and 65,536-log limits; a later action snapshot invalidates the handle and reports an error instead of returning another snapshot’s log. The interface shows a partial-import notice and dropped log count, lets the user select peer, skill and action, and pages action rows. It does not replay logs through the parser.

The original-form comparison and physical UI interactions remain unverified on Windows; independent review remains pending because of the existing quota limit. The separate plain action list orders by descending time sorter/time.

## Managed aggregate table core

`CaptureCategoryActions` now also constructs revision-owned `DamageTypeData` peer groups and `AttackType` skill groups with copied `MasterSwing` rows. This follows `FormByCombatantLookup.ShowLookup`: outgoing victim/incoming attacker, ordinal peer identity, aggregate plus skill insertion (including All collision), peer parent resolved from the original encounter, fresh action Tags, null ParentEncounter and Special=None. Dnum value/display fields are copied instead of sharing ACT’s mutable Dnum instance; this is an intentional snapshot-isolation difference. Parent combatants remain original live ACT objects, as in ACT; callbacks inspecting the parent do not receive frozen whole-encounter state.

`HostEnvironment.ReadLookupTable(revision, query, peer?, skill?)` runs on the owner thread under CombatGate and the existing read-only callback guard. Omit peer for category rows, omit skill for that peer’s skill rows; supply both for action rows. Use matching Category/Attack/Action column catalog revision and encounter ID. Read the registered column keys, not labels. Default order is descending: peer damage; skill mDSort/mDSort2 then damage; action aTSort/aTSort2 then TimeSorter/time. Explicit TableSort reuses registered comparers. Existing bounded ordering detects comparer exceptions/inconsistency; cell errors remain per-cell.

Limits: 16,384 admitted actions, 4,096 peers, 32 selected columns, 256 returned rows, 32,768 derived action rows, existing 4 KiB cell/8 MiB response text and comparison budgets. Replacement action capture, closed host or changed column catalog is rejected; snapshot capture and lifecycle reentry are blocked during callbacks. Arbitrary native callback hangs or direct mutation of plugin-accessible objects are not prevented by this managed guard.

These contracts were checked against decompiled ACT ShowLookup/AfterSelect and AttackType/MasterSwing CompareTo plus synthetic managed callbacks; the native form was not executed. Bridge/Rust table transport and the GUI aggregate table use the same owned revision. The table starts with registered default-visible readable columns and allows per-lookup column selection, sortable displayed columns, paging and peer/skill drill-down. The initial selection uses the saved shared category, attack and action table preferences in their configured order, reconciling temporarily unavailable plugin keys without changing the saved preference. If no saved preference exists, registered defaults are used. The lookup column picker changes a local draft, including order and an empty selection; “Save shared columns” explicitly persists it to the same app settings. Absent plugin keys and their prior visibility/order are preserved, and a dirty shared table editor draft is not overwritten. Failed saves retain both the prior file and lookup draft. An accepted app-settings write may complete after the session ends, but its old view receives no success message; the new durable settings are synchronized in memory. If a draft references a plugin column that disappears, it remains intact and the request reports the missing column; retry after registration returns or explicitly discard the draft. A registration change after the pre-save check can race the app-owned file write; it is not a cross-process transaction. The empty selection checks snapshot ownership without invoking a column callback and reports that the row count is unavailable. ACT native visual layout remains different.
